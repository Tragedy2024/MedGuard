## 这是什么

一个面向医院场景的数据查询平台。医生和病患**用中文提问**，院内查询结果来自医院主库；
医学科普来自标明来源的项目整理资料和可选开源数据。

患者的「智慧医生」让大模型先理解普通自然提问中的对象、否定、指代和所问内容，
再由服务器选择记录查询、知识检索或澄清。明确的常用单一问法保留本地快速处理。
需要综合解释时，模型只能基于检索证据组织回答；证据不足则说明未覆盖的部分。
界面分别展示语义理解状态、医学证据状态及院内数据访问审计状态。

患者端只有一个输入框，服务端在**智慧医生 / 查询控制台**两个功能中选择。
智慧医生处理医学知识，查询控制台再区分**本人记录 / 医院业务**两个查询范围；医生与管理员则保留
「**可信问答（查询控制台）**」这一级工作台。路由只负责分流，不授予数据权限——
**Jev/LLM 不决定数据访问**，通用查询与本人记录一样要过层一准入和层二审计。

但它真正在做的事在另一侧：

> 大模型要参与查询，数据就必须进它的上下文。
> 而 Agent 拆出来的**中间结果**——那些用户永远看不到、却要送进模型推理的子查询结果——
> 从来没有被审计过。**这里就是数据离开医院边界的地方。**

列掩码管不住它（中间结果不是"输出"），行级权限管不住它（那些数据是"合法查到的"），
事后过滤管不住它（召回率 0–16.7%，且会破坏查询功能）。

医盾在**执行之前**对查询**计划**做静态审计，补上这个位置。

## 机制

```
用户提问（自然语言，携带令牌）
    │
    ▼
┌─ 翻译 ──────────────────────────────────────────────────────┐
│ 自然语言  ──▶  查询计划 [{id, description, sql}, …]          │
│ 缓存优先，未命中才调 LLM。LLM 只翻译，不生成数据答案。       │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
            ┌──【层一】准入检查 ──┐
            │ 这个令牌能发起       │──拒绝──▶ 固定文案，不查库、不执行
            │ 这个查询吗？         │
            └──────────┬──────────┘
                       │ 通过
                       ▼
            ┌──【层二】医盾审计 ★ ─┐
            │ 零 LLM · 零查库       │
            │ sqlglot 纯 AST 静态分析│
            │ 列级 / 跨域 / 派生信息流│
            └──────────┬──────────┘
                       │ 改写后的计划 + L0–L3 降级
                       ▼
                   执行 ──▶ 医院主库 ──▶ 结果
```

**层一**是常规授权——"你不该问这个"，**不是本项目的创新**。
**层二**才是——"你能问，但这条计划会多带数据出去"。

把两者混为一谈，就会把常规授权包装成研究成果。这个区分必须讲清楚。

### 为什么"零 LLM"是安全属性，不是性能优化

| | 提示词防御 | 医盾 |
|---|---|---|
| 换一个宿主 Agent | 只降 1.4–9 倍，**不清零** | 检测率不变 |
| 能否被提示注入绕过 | **能** | **不能** |
| 能否被当作混淆代理去查库 | 可能 | **不能** |

审计引擎没有提示词、不访问数据库、输出确定——
三条合起来就是经典安全里的**引用监视器（Reference Monitor）**：
完全中介 + 防篡改 + 可验证。

> 一句话：在 Agent 和数据库之间，加一道**无法被说服**的执行点。

## 智慧医生的知识层

医盾管的是"什么**不许**进模型"；这一层管的是"什么**可以**进模型"——
**不是"我们用了 RAG"，而是"进模型的东西是被挑过的、且来源清楚"**。

### 一个输入框：先理解，再由规则选择管线

明确的常用单一问法走本地快速处理；其他自然提问在配置模型密钥后默认启用语义理解。
模型只返回有限 JSON：对象、原话片段、否定标记、任务、字段和查询范围。
服务器校验格式、置信度和实体出处，拒绝模型自行添加的 SQL、患者编号和推断疾病。
同一请求的理解结果在患者路由与智慧医生之间复用，不重复调用模型。

服务器据此选择顶层功能 `smart_doctor` 或 `query_console`，后者再区分 `self` / `hospital` 查询范围。
`personal_record`、`general_query`、`knowledge` 保留为内部执行策略，`clarify` / `unsupported` 是待确认或不支持的状态，不是额外功能；
检索同时按对象和字段过滤，多对象或多诉求证据不全时明确标记不足，避免用首个关键词资料卡代答。
本人记录和通用查询仍经过统一层一准入、层二审计与执行绑定，模型输出不构成授权。

所有分到查询控制台的问题，包括本人检验、用药、费用、就诊日期和医院业务，
均直接调用原控制台的 `run_direct_query`：查询计划缓存 → 未命中时 NL→SQL → 准入与审计 → 只读执行及报告。
统一入口不再用智慧医生的固定模板代替查询控制台，也不在查询结果后自动套用医学解读。
“血糖正常吗”在没有明确本人记录上下文时，给出“智慧医生 / 查询控制台”两个确认选项，确认前不读取本人记录。
费用的语义识别通过后不再要求匹配固定问句，但仍检查本人诉求、他人信息、未来估价和未支持的筛选条件。

语义模型只接收经过常见姓名、手机号、证件号和记录编号规则遮盖的提问，以及已知知识话题；
不接收患者记录、令牌或数据库返回值。该遮盖属于输入最小化，不能代替完整的隐私去标识化治理。
`MEDGUARD_SEMANTIC_ENABLED=1` 默认启用；`MEDGUARD_SEMANTIC_TIMEOUT_SEC=8` 限制单次等待，
最多两个未完成调用。超时、繁忙或校验失败会在界面说明并请求澄清，不静默用无关卡片代答。
没有密钥或主动关闭时保留原有确定性功能。语义理解使用模型与医学答案生成使用模型分别计量；
“审计阶段零 LLM”仅指安全审计，不代表整个问答不调用模型。

### 事实来自开源数据集，解读来自 AI

| 块 | 内容 | 来源 |
|---|---|---|
| 院内数据 | 患者本人的化验 / 用药 / 诊断 | **医院主库**（经层一 + 层二审计） |
| 就诊科室建议 | 症状 → 相关疾病 → 科室分布 | 可选的 **OpenCMKG** 本地派生数据 |
| 疾病条目 | 关联症状、关联检查及科室 | 可选的 **OpenCMKG** 本地派生数据 |
| 通俗解读与建议 | 把上面的事实讲给患者听 | **AI**，界面标注「AI 智能导诊」 |

> **为什么要分开**：事实可以确定、可离线、可复现；而"这意味着什么"需要语言
> 组织能力。**把确定的部分留给数据，把解释的部分交给模型并标注**——这与医盾
> 「零 LLM」的立场一致：能确定的不交给模型，交给模型的不假装确定。

### 数据集怎么用（可复现、可审计）

```
backend/scripts/build_dataset_tables.py      抽取脚本（随仓库开放）
        │  读 OpenCMKG 的原始三元组
        ▼
backend/demo/symptom_departments.json        本地生成，已由 .gitignore 排除
backend/demo/disease_facts.json              本地生成，已由 .gitignore 排除
```

**抽取逻辑在代码里，不是在文档里声称。** 使用者在确认符合上游用途限制后，
自行下载固定版本的 OpenCMKG 三元组并运行脚本，即可在本地复现派生文件。
由于上游未明确授予派生数据再分发权，仓库不提交原始数据、派生 JSON 或其向量缓存。

**新克隆没有派生文件时**：`dataset_kb` 回退到随仓库提交的
`disease_facts.synthetic.json` / `symptom_departments.synthetic.json`
（MIT，`_meta.source` 明确标注「合成演示数据（非临床）」）。
真实 OpenCMKG 派生文件存在时优先使用真实文件；真实文件存在但损坏时
**不**回退，避免把数据故障伪装成正常。一条命令准备完整数据：

```bash
cd backend
python scripts/prepare_demo_data.py --download --proxy http://127.0.0.1:7897
python scripts/prewarm_rag.py
```

构建脚本读取标准 CSV，将科室、症状与检查关系生成三份本地派生 JSON。
疾病卡保存原始行号与完整列表，默认页面每个字段最多展示五项。科室冲突保留候选，
单一科室字段仅在结果唯一时生成。口语映射来自脚本中的显式清单。

`--output-dir` 可将文件构建到暂存目录。`--review-log` 可另存解析失败、污染值及待复核的
`SameAs`、药物、治疗与并发关系，其中上游并发关系拼写为 `disease_acompany_disease`。
这些待复核记录保存在本地审核文件。新数据标记为未经临床复核。

### 诚实的边界

- 症状导诊展示图谱关联数量靠前的候选科室。关联数量表示数据集内的疾病分布。
- **急诊横幅由知识库 acuity 分级与红旗规则层共同决定**（见「红旗规则层」一节）：
  检验解读命中危重及以上档位、或任何路径命中红旗词（胸痛等），都会弹横幅；
  红旗层独立于 LLM 与知识图谱，命中即无条件升级。
- **许可**：OpenCMKG 为「**仅学术研究，不得商用**」，且没有明确的派生数据再分发授权。
  本仓库仅开放清洗、转换、索引和评测脚本，不分发原始或派生医学事实数据。
- 检验数值分档与用药说明**仍是本项目自建的仿真内容**（`demo/smart_knowledge.yaml`），
  尚未迁移到开源来源。

### 红旗规则层（独立于模型的安全网）

急诊横幅由**确定性规则**驱动，不依赖 LLM 与知识图谱（2026-09 代码评审 P1）。
规则见 `backend/backend/redflags.py`：胸痛、呼吸困难、意识障碍、大出血、
严重过敏、心脑血管急症共 6 组高特异表述，命中即把 `advice.urgent` 置为
True 并在建议文本最前加入急诊指引——即使 AI 未判急症、知识图谱未覆盖、
未配置 API Key 也一样升级。精度优先：不收录「胸闷」「心疼」等模糊词，
避免「人人弹警告」稀释真信号。红旗判定零 IO、零网络、可单测。

### BGE 混合检索与自动降级

系统默认使用 BM25 + BGE 两路召回，再以 RRF 融合排名。桌面环境优先使用
FlagEmbedding；Vercel 等轻量运行环境自动改用 FastEmbed 的 ONNX 版
`bge-small-zh-v1.5`，无需打包 PyTorch。精排已移除；两种 BGE 后端均不可用，
或模型加载、建索引、查询阶段发生故障时，才回退到完全离线的 BM25。

```bash
pip install -r backend/requirements-rag.txt

# CPU 演示推荐 small；有 GPU 或需要多语言时可改成 BAAI/bge-m3
MEDGUARD_RAG_DENSE=1
MEDGUARD_RAG_DENSE_MODEL=BAAI/bge-small-zh-v1.5
```

阈值必须以项目自己的中文医疗金标集校准；相关性分数不是医学正确性评分。
检索低于阈值时返回空证据，不会为了凑满 top-k 而强行注入无关上下文。

### 按需检索策略与元数据过滤

患者统一入口先理解问题，由服务端选择智慧医生或查询控制台，再为查询控制台确定本人记录或医院业务范围；
进入知识层后，智慧医生再通过 `knowledge/strategy.py` 选择取数路径，借鉴
Adaptive-RAG 的按需选择思想，采用可追踪的确定性规则；没有训练或引入原论文的
分类模型。本人检验/用药记录仍走身份准入、SQL AST 审计及只读执行。
明确的疾病/症状事实优先查表，通用检验范围和药品注意事项直接读取知识库，
不为这类问题访问本人数据库或调用生成模型。
解释和比较问题进入混合检索；对象不明确时澄清，未收录子型时说明资料缺失，
不再用父疾病条目代替“1型/2型”等明确子型。

`hybrid.search(..., filters=MetadataFilter(...))` 支持类型、规范实体、字段、来源、
来源版本和质量层级条件。同一维度内取并集，不同维度取交集；BM25/BGE 都先过滤
再截取各自候选，不会在空结果时自动放宽条件。YAML 核心证据保留规则同样受过滤
约束。字段过滤还会限制送入生成模型的原文，避免把整张事实卡的无关字段一起发送。
当前仍按原有文档粒度建立向量索引，没有新增数据库、精排模型或自动网络扩检。

患者统一入口 `POST /api/patient/ask` 返回 `feature`、`query_scope`、内部策略 `route` 与 `reason`；
`interpretation_feature` 保留兼容字段，查询控制台返回原有查询结果，当前不自动追加智慧医生解读。
接口在内部复用现有
智慧医生与查询管线；进入知识层后，响应仍包含可选的 `retrieval_plan`（实际选择的
策略、理由及元数据条件）。它用于开发与评测追踪，不授予访问权限；没有模型 Key 时
仍跳过 AI 兜底检索。第二知识源仍默认关闭，需要单独评测后开启。回归测试：
`python -m pytest tests/test_adaptive_retrieval.py tests/test_knowledge_rag.py tests/test_smart_doctor.py`。

### Jev 公开知识分类实验（可选）

在 `.env` 设置 `JEV_API_KEY` 并重启后端，Jev 会自动启用。可以直接输入
“甲状腺结节是咋回事”“帕金森病这几个字是什么意思”或“黄斑变性是个啥情况”验证。
如果旧配置含 `MEDGUARD_JEV_ENABLED=0`，将值改为 `auto`。如果旧清单是
`MEDGUARD_JEV_APPROVED_QUESTIONS=[]`，删除该行即可使用内置示例。

自定义 `MEDGUARD_JEV_APPROVED_QUESTIONS` 会替换内置清单，仅填写合成或人工审核过的
非敏感问句。只有规则未识别且与清单完整匹配的问句会发给 TypeSafe。Jev 提供公开
知识分类或澄清提示，疾病对象由本地知识库匹配。本人记录仅通过本地判定、身份准入
和审计流程读取。**Jev 不参与患者统一入口的路由判定，也不决定任何数据访问权限**；
它只在本地规则完全未识别、问句精确命中白名单时影响公开知识分类或检索策略。
调用固定使用 `jev-1.14.0`，默认 2.5 秒内未得到可用结果则沿用
常规兜底（`MEDGUARD_JEV_TIMEOUT_SEC` 可调，范围 0.1–10 秒）。

### OpenCMKG 第二知识源（默认关，可选的召回扩充）

使用者自行生成的 OpenCMKG 检索文档（固定版本实测约 1.5 万条，包含疾病、症状、
检查和科室，**不含药物与治疗**）可纳入混合召回。未生成时系统自动只使用
人工 YAML 知识源：

```bash
MEDGUARD_RAG_OPENCMKG=1
MEDGUARD_RAG_OPENCMKG_WEIGHT=0.7   # 来源权重：YAML 1.0、OpenCMKG 0.6～0.8
```

开启后 BM25/BGE 各自对两套语料召回，按来源权重做 RRF 融合；YAML 有可靠命中
时 top_k 至少保留一条人工证据。OpenCMKG 只贡献**事实召回**、不参与直接诊断；
检索文档由 `build_dataset_tables.py --export-docs` 从固定 SHA-256 的原始三元组
在本地生成，文件受 `.gitignore` 排除。关闭（默认）或文件不存在时，行为与纯
YAML 检索完全一致。语料向量落本地磁盘缓存
（`backend/data/dense_*.npy`，gitignore，键=推理后端+模型名+文档内容哈希），且 BGE
已缓存时强制纯离线加载——演示/评测不因网络抖动退化成 BM25。

检索质量有金标评测支撑：86 条四类问法（2026-10 新增 20 条口语疾病问法）、
四路配置对照（纯 BM25 / +BGE / +OpenCMKG / 全量混合）见
[`docs/research/2026-10-04-retrieval-eval.md`](docs/research/2026-10-04-retrieval-eval.md)。
先按上文生成本地派生数据，再复现：`python scripts/eval_retrieval.py --all`。

回答安全性另有**医学评测**（自动化风险代理指标，未经临床复核）：四维 14 例
——红旗升级 / 拒答适当 / 证据忠实度 / 有害误导率，见
[`docs/research/2026-10-07-medical-safety-eval.md`](docs/research/2026-10-07-medical-safety-eval.md)，
复现：`python scripts/eval_medical_safety.py --offline`（确定性维度）/

| 账号 | 密码 | 身份 | 能进哪些页 |
|---|---|---|---|
| `admin` | `medguard` | 医院管理员（信息科） | 数据源 / 安全策略 / **用户管理** / 可信问答（查询控制台）/ 安全报告 |
| `doctor` | `medguard` | 医护人员（医生001·心内科） | 可查范围 / 可信问答（查询控制台）/ 安全报告 |

> 患者端只有一个输入框「智慧医生」：本人记录、通用查询和知识问题都在这里问，
> 由服务端本地确定性规则自动路由；**路由与准入不在 Jev/LLM 手里**。
> 医生与管理员保留「**可信问答（查询控制台）**」一级工作台，用于核对 SQL 与
> 审计回执。同一个通用查询问题，医护令牌与病患令牌给出不同结果——
> 这正是演示矩阵成立的前提。
> 身份**不可在界面上随手切换**，必须退出后重新登录——
> 对一个以安全为卖点的产品，"能随便切身份"本身就是可信度问题。

**这三个账号存在后端**（平台元数据库的 `users` 表，口令是 PBKDF2 哈希，
不是明文），登录由 `POST /api/auth/login` 判定并**签发带 HMAC 签名的令牌**，
所有收令牌的端点都会验签。管理员登录后可在「用户管理」页建新账号——
医院里开号是信息科的活，所以**没有自助注册**；非管理员调用建号接口返回 403。

## 演示动线：双令牌矩阵

同一套平台、同一个问题，**两类令牌给出不同结果**。这是权限隔离最直观的证明。
患者不需要切换到另一个查询系统：她在「智慧医生」唯一输入框里直接问，服务端
确定性路由先把问题分到本人记录、通用查询或知识库；通用查询再走层一准入和层二审计。

| 问题 | 医护令牌（可信问答） | 病患令牌（智慧医生输入框） |
|---|---|---|
| 我上次的血糖是多少 | —（医护无此问法） | ✅ 自动路由本人记录 + 层二通过 |
| 心内科有哪些医生 | ✅ 放行 | ✅ 自动路由通用查询，放行（不涉及患者表） |
| 统计各科室接诊量 | ✅ 放行（对照组，L0 / 0 事件） | ❌ 自动路由通用查询 → **层一执行前拒绝** |
| 糖尿病患者产生了多少费用 | ✅ 放行 + **层二跨域拦截**（L2 / 3 事件） | ❌ 自动路由通用查询 → **层一执行前拒绝** |
| 按诊断结果分类统计患者数 | ✅ 放行 + **层二派生拦截**（L2 / 2 事件） | ❌ 自动路由通用查询 → **层一执行前拒绝** |
| 导出患者基本信息核对表 | ✅ 放行 + **层二禁止列**（L2 / 1 事件） | ❌ 自动路由通用查询 → **层一执行前拒绝** |
| 得这个病的有多少人 | —（医护无此问法） | ❌ 自动路由通用查询 → **层一执行前拒绝**（L3 / 无结果） |

> **关于患者端的通用查询**：患者导航中没有「可信问答（查询控制台）」入口，她只有
> 一个输入框。输入"统计各科室接诊量"时，服务端先把它路由到通用查询，再由层一在
> 执行前拒绝。路由只决定"走哪条链路"，**不授予任何数据权限**；最终裁决始终是
> 层一准入，绕过界面直接调 API 同样如此。
>
> **可现场演示的层一拒绝是「得这个病的有多少人」**——在智慧医生输入框里输入
> 即可看到执行前拒绝。
>
> **离线演示提示**：患者端预置问法里，可稳定复现的通用查询放行是
> 「心内科有哪些医生」，越权拒绝是「得这个病的有多少人」。其他医护专用问法
> 若未收录且当前无模型翻译，会返回可读的“暂未收录”；一旦有可执行计划，
> 层一仍会在执行前拒绝。不要把“未收录”误讲成“层一拒绝”。

层一拒绝时返回**固定文案，不做任何改写**：

> **「该查询涉及其他患者信息，无法提供。」**

不假装"查不到"——含糊的失败会让用户反复换问法试探。明确告知边界是可解释性，
且对所有涉他查询统一措辞，避免通过错误信息差异反推数据存在性。

### 界面上必须能被当作证据的三件事

1. 指标条的 **`LLM 调用 0 / 数据库访问 0`**——"零 LLM、零查库"的可验证形式
2. **改写前后的 SQL 对比**，哪一列、因为什么、被怎么处理了
3. 报告页可回看的**历史留痕 + 一键导出 JSON**（含审计—执行绑定：
   `decision_id`、改写后计划的 SQL 哈希、实际执行哈希与时刻——证明
   "执行的就是审计通过的那份"，评审 B5）

## 关键设计决策

| 决策 | 理由 |
|---|---|
| **前期审计引擎边界清晰** | 审计耦合点收敛在 `deps.py`；本次医疗适配与产品实现单独记录 |
| **层一与层二分开实现** | 层一是常规授权（非创新），层二才是算法创新 |
| **安全策略每数据源一份，不按角色分** | SSA 描述数据自身的属性，与谁在问无关 |
| **病患令牌全称禁止涉他数据** | "可反推性"不可判定（需知结果基数，而基数要查库）；全称禁止是可判定的 |
| **患者只有一个输入框，路由在服务端** | 患者不必理解查询模式；本地确定性规则只负责分流，不授予权限；Jev/LLM 不决定数据访问，通用查询仍走层一/层二 |
| **演示库 SSA 手写而非 LLM 生成** | 标注工具不生成跨域规则；blocked 标签需人工定案 |
| **策略页仅管理员可见** | 那是平台管理职能。与"层二与角色无关"不矛盾——后者说数据属性，前者说谁能改标注 |
| **界面上只用中文业务别名** | 向医生展示 `clinical_records.impression` 只会把产品退回成开发者工具 |
| **缓存计划而非答案** | 命中缓存后照样走层一与层二，安全演示一点不打折 |
| **平台元数据库与业务库分离** | 前者是平台自身状态，后者是被审计对象 |
| **疾病意图才扫数据集疾病名** | 7495 个疾病名只在「想了解/做什么检查」等明确意图下精确最长匹配，不做模糊匹配——错配疾病比答不上来更糟（评审 A1） |
| **数据源就绪门禁** | 接入真实库前扫描 schema 与 SSA 标注的差距，存在未标注表/列即「未就绪」；严格模式禁止启用，演示库恒为兼容模式。真实库经 `MEDGUARD_DATASOURCES`（JSON）登记 id→db_path 后入册，按各自库扫描与执行（评审 B6） |

## 诚实的边界

这一节不是免责声明，是这个项目的可信度所在。

- **翻译准确率不是 100%。** 当前项目自有查询计划适配器仍可能误解任意中文问法；
  预设问法和安全审计只能降低演示风险，不能替代真实业务验证。
- **演示走预置查询与本地缓存**，NL→SQL 那一步不实时调用。
  理由：产品创新点全在审计侧；而模型单次翻译要几十秒，会让视频录制不可控。
  **审计与准入判定 100% 真实**，缓存路径与实时翻译路径的实测结果一致
  （同为 L2 / 3 违规 / 1 改写）。
- **患者统一入口用语义理解辅助、本地守卫选择功能，不是自训练的分类器。** 常见明确问法可直接处理；
  模型只输出受限结构，不授予数据权限。功能或查询范围不明确时先确认。误路由风险需按最终回归
  问句清单核对，不能把"路由正确"当成语义理解能力。
- **本引擎不防御小样本聚合推断**（如罕见病计数）。这是"可反推性不可判定"的必然结果，
  由层一的全称禁止在病患侧兜底。
- **SSA 是列级标注**，不编码值或行。
- **审计的是"查询计划"这一层**。若 Agent 绕过计划直接执行 SQL，中介就不完整。
- **未标注的列默认放行**（`fail-open`）。所以策略页的"审查状态"不是装饰，
  它对比库中实际列与策略标注，把漏标的列标出来——这是产品层能提供、
  算法层看不见的价值。
- **当前为仿真数据**，非真实医院数据。所有姓名/证件号一律"一眼假"（`患者001`、`TEST-000001`），
  绝不使用看似真实的个人信息。
- **无暗色模式，无隐私政策/服务条款链接。** 医疗数据产品化时应补。

### 已知未覆盖（刻意的）

前端无组件级单元测试；e2e 覆盖关键路径，但不是全量交互回归；无性能与并发测试、
无多数据源测试。原因与风险见 `docs/TestPlan.txt` 第七节。

### 契约变更流程

`src/api/types.ts` 是生成物，**禁止手工编辑**。业务代码一律从 `src/api/models.ts` 取类型。

```bash
# 1. 改后端 backend/schemas.py
# 2. 重启后端，重新导出与生成
curl -s http://localhost:8000/openapi.json -o frontend/openapi.json
cd frontend && npx openapi-typescript openapi.json -o src/api/types.ts
npx tsc -b          # 有错就是契约对不上——这正是这一步的目的
```

`models.ts` 里的联合类型（`TokenType` / `DegradationLevel` / `EclLabel`）
是**从契约派生**的，不是手写。后端一改取值，前端立刻编译失败——这是有意为之。

### 不要提交
