## 2. 需求分析（重做版）

用户给出的定位（原文）：

> 项目定位是服务于医院的查询系统。项目中假设存取的是医院所有的数据，当前版本为医院数据仿真版本。
> 使用群体为医护人员和病患。项目主要目的就是不泄露中间信息，且可以允许非数据库管理专业人员
> 也可以随时有效的获取到权威准确的医院相关信息。

拆解出四条硬约束：

| # | 约束 | 含义 |
|---|---|---|
| 1 | 用户是**非数据库专业人员** | 不能要求用户会写 SQL；自然语言提问是唯一入口 |
| 2 | 答案必须**权威准确** | 见 §3 |
| 3 | **不泄露中间信息** | 这是算法层的核心能力，也是产品要凸显的点 |
| 4 | 数据是**医院仿真版本** | 不接真实 HIS 系统，全部虚构 |

### 2.1 "权威准确"怎么落地

用户确认：

> 权威准确就参考论文仓库中 NL2SQL 查询即可，"答案来自主库 + LLM 只翻译不回答"这个理解是准确的。

即：**主库是唯一事实来源，LLM 只做自然语言 ↔ SQL 的翻译，绝不参与生成答案内容。**

这是可验证的产品主张，不是宣传语。演示时可以对比"让 LLM 直接回答"与"LLM 只翻译 + 主库回答"在同一问题上的差异。

> **诚实声明**：论文仓库中 NL2SQL 的 EX（执行准确率）为 62–77%，不是 100%。
> 演示话术不得暗示翻译环节零错误。真实主张是"**答案一旦产出，其来源是主库而非模型**"。

## 4. 两层安全模型 ★ 本次会话最重要的结构发现

### 4.1 从"按角色审计"到"按数据属性审计"

中途我提出过一个错误方案：**为每个角色生成一份 SSA 策略文件**。

**为什么错**：这把**授权**和**审计**混为一谈。
SSA（安全敏感属性标注）描述的是**数据自身的属性**（这一列是不是个人信息），
与**谁在查**无关。同一列对任何角色都是"受控"的。

正确模型是分两层：

```
【层一】准入 —— 令牌 → 这个查询能不能发起
        常规权限控制。确定性强、执行前生效。
        ★ 不是算法创新，是产品必需的配套

【层二】中间结果审计 —— 查询计划 → 会不会泄露
        零 LLM、零查库、纯 AST 分析。三审计维度。
        ★ 这才是算法创新，也是产品要凸显的部分
```

**层二与角色无关**，因为 SSA 描述数据属性而非用户属性。这个性质让策略只需按数据源维护一份。

### 4.2 零 LLM 为什么是安全属性（而不只是省钱）

参考监视器（Reference Monitor）的三条经典要求——**必须拦截每一次访问、必须不可绕过、必须足够小可验证**。
零 LLM 直接满足后两条：

- **无提示注入面**：不调模型 = 没有可被污染的输入通道
- **无困惑代理（confused deputy）面**：不访问数据库 = 没有可被诱导执行的权限
- **确定性 = 可形式化验证**：同样输入永远同样输出

### 4.3 本次会话中"本来可以用但没用上"的关键论证

论文仓库里有现成的对照实验，展示了**提示层防护的跨宿主衰减**：

| 方案 | 机制 | 跨宿主表现 |
|---|---|---|
| B4 安全提示 | 在 prompt 里叮嘱模型别泄露 | QSG S-VR 只降 1.4–9 倍，**不归零** |
| B3 事后过滤 | 拿到结果再过滤 | S-AR 仅 0–16.7%，且**破坏功能** |
| **B2 确定性审计（本方案）** | AST 静态分析 | **S-AR 100%，跨宿主不变** |

**这张表是答辩时最有力的论据**：它不是"我们的方法更好"，而是
"提示层防护在换模型后会衰减，确定性审计不会"——这是可证伪的工程结论。

### 4.4 检测效能（实测数字，可直接引用）

| 指标 | 值 | 来源 |
|---|---|---|
| 精确率 | 100%（误报 0/66） | `NL2SQL/results/rq3/` |
| 召回率 | 100%（漏报 0/20） | 同上 |
| blocked 列检出 | 10/10（L2=8 / L3=2） | 同上 |
| 单查询耗时 | < 20 ms | 同上 |

> 这些数字**必须来自结果文件**，不得凭印象填写。前端展示的效能指标直接读 `GET /api/metrics/detection`，
> 该接口的数值硬编码在后端 `reports.py`，来源标注为 `NL2SQL/results/rq3/`。

### 4.5 已声明的边界（诚实交代，不是缺陷）

**罕见病推断攻击可以穿过全部三个审计维度。** 例如：

```sql
SELECT COUNT(*) FROM patients WHERE diagnosis = '某罕见病'
```

若全库只有 1–2 例，这个计数**就是个体信息**。但审计器不会拦——因为：

SSA 是**列级**标注，它知道 `diagnosis` 是受控列；但它不知道**值的分布**（几例算罕见？）。
要判断"这个聚合结果能否反推个体"，需要知道结果基数，而基数**要查库才知道**——
这与"零查库"的根本前提冲突。

**这是设计边界，不是 bug。** 解法在层一：病患令牌的任何涉及其他患者数据的查询一律拒绝
（§3.2 的全称规则），这正是用户把规则加严的原因。层一是确定性的、执行前的、且**不需要改动算法层一行**。

## 5. 算法层接口（源码核实，2026-09-10）

### 5.1 三个接触点

```python
# ① 加载策略
from ssa.loader import load_ssa                    # src/ssa/loader.py:132
ssa = load_ssa(db_id=datasource_id, ssa_dir=<数据源专属目录>)

# ② 取违规详情（UI 事件卡片用）—— 管线返回里没有这个
from auditor.base import SecurityAuditor           # src/auditor/base.py
auditor = SecurityAuditor(ssa)
audit_results = auditor.audit_all([{"id": sq["id"], "sql": sq["sql"]} for sq in plan])

# ③ 取改写与降级（对比面板与徽章用）
from security_auditor import run_security_auditor_pipeline   # src/security_auditor.py:762
out = run_security_auditor_pipeline(
    decomposition_plan=plan, db_id=datasource_id, ssa_dir=<数据源专属目录>)
```

> **为什么是三个而不是两个**：`run_security_auditor_pipeline` 只返回违规**计数**，不返回违规**详情**。
> 界面要展示"哪一列、什么类型、为什么"，必须直接调 `SecurityAuditor.audit_all()`。
> 两者都是零 LLM、零查库的纯 AST 计算，各调一次是安全的。
>
> `run_security_auditor_pipeline` 在 `src/security_auditor.py`，**不在** `src/auditor/base.py`。

### 5.2 实测发现的坑

**坑 1：`audit_report` 有三种形状，随执行路径变化**

| 路径 | 键 |
|---|---|
| 无 SSA | `passed`, `violations`, `note` |
| 干净（零违规） | `passed`, `violations`(=`[]`), `dimensions_checked`, `rewrite_log`, `semantic_degradation` |
| 有违规并改写 | `passed`, `violations_before`(int), `violations_after`(int), `rewrites_applied`, `rewrite_log`, `semantic_degradation` |

**有违规时 `violations` 键根本不存在**，`dimensions_checked` 也消失。前端契约必须按可选字段处理。

**坑 2：`rewrite_log` 是字符串数组**，非结构化对象。改写 diff 面板需自行做行级 diff 或解析字符串。

**坑 3：未标注列默认放行（fail-open）** —— 见 §7.3，这是安全相关的。

### 5.3 三处真实纠错记录

会话中基于源码核实修正了自己写错的三处：

1. **导入路径写错**：曾写 `from auditor.base import run_security_auditor_pipeline`，实际在 `src/security_auditor.py:762`。
2. **`audit_report` 形状假设错**：曾假设有统一的 `violations` 数组，实测有违规时该键不存在。
3. **数据流顺序错**：曾把层一放在预设查询库之前，但层一判定的是 SQL 计划，计划必须先存在。
   正确顺序：`NL→SQL → 层一 → 层二 → 执行`。

## 6. 跨域规则为零：诊断结论

### 6.1 问题

用户提问："这个跨域规则 0 数据是数据集的问题还是设计有bug导致的？"

### 6.2 结论：**标注流程的缺口**，不是数据集问题，也不是代码 bug

证据链：

1. **实证**：手工往 `thrombosis_prediction.yaml` 写入一条跨域规则后，审计器**正确触发**
   （3 个反例上 1 真阳、0 假阳）。代码路径是通的。
2. **数据具备条件**：`thrombosis_prediction` 存在真实外键 `Examination.ID → Patient.ID`，
   两侧都有受控列。也就是说，这个库**本该有**跨域规则。
3. **提示词里没有这个字段**：`annotator.py` 的提示词只请求 `column_labels`，
   全文不含 `cross_domain` 字样。自动标注**根本不会产出**跨域规则。
4. **人工审核记录显示是有意留空**：11 个 BIRD 库的 YAML 里 `## 跨域规则` 段全部写着
   `（尚未定义）`；20 个 Spider 库**完全没有这一段**。

**影响**：论文仓库 31 个库的跨域规则实际生效数为 **0**。
演示库的跨域规则必须**手写**，不能依赖自动标注。

## 7. 演示库设计（医院数据仿真版）

### 7.1 表结构：5 表

原本设计 8 表，后发现 `diagnoses` / `medications` / `lab_tests` / `imaging` 四张表**结构同构**
（都是 `visit_id + patient_id + 若干列`），遂合并为一张 `clinical_records`，用 `record_type` 区分。

| 表 | 说明 |
|---|---|
| `patients` | 患者主档 |
| `staff` | 医护人员 |
| `visits` | 就诊记录 |
| `clinical_records` | 临床记录（`record_type` = diagnosis·medication·lab·imaging） |
| `billing` | 费用结算 |

**关键设计决策**：`patient_id` 在 `visits` / `clinical_records` / `billing` 上**反规范化保留**（即使可通过 `visit_id` 关联得到）。

**理由**：层一准入判定需要能直接看到 `patient_id` 出现在查询里。如果只能通过 JOIN 得到，
判定就需要做连接推导，复杂度上升且容易出错。这是为安全判定做的**有意的反规范化**。

### 7.2 仿真数据必须「一眼假」

- 患者：`患者001`、`患者002`……
- 身份证：`TEST-000001`
- 电话：`TEST-PHONE-001`
- 医生：`医生001`

**绝不使用看起来真实的姓名、身份证号、手机号**——即使是编造的。避免任何"疑似真实个人信息"的观感风险。

### 7.3 ★ 未标注列默认放行

源码核实（`src/ssa/loader.py:63`）：

```python
if not matches:
    return ECLLevel.FREE
```

**策略里找不到某列 → 按「自由」处理 → 医盾静默放行，无告警、无痕迹。**

这使得"策略是会腐烂的资产"从修辞变成**精确的安全属性**：
往库里加一列、忘了标注 SSA，该列就脱离了审计范围。

产品层的应对：`GET /api/policies/{id}` 返回 `review_status` 字段，对比**库中实际列**与**策略标注**，
把未标注的列标出来。并有阻塞性测试 `test_all_demo_columns_are_labeled` 守住演示库不出现这种缺口。

> 这是产品层能提供、算法层看不见的价值——也是模块②的核心卖点。

### 7.4 三条硬约束（演示库必须满足）

1. **每条预设查询都要有可展示的触发** —— 演示时不能出现"什么都没发生"
2. **病患查本人数据的查询必须有真实结果** —— 空结果会被误读为"系统坏了"
3. **医护的跨域查询必须真的触发跨域规则** —— 这依赖 §7.3 的手写规则

## 10. 术语表

| 术语 | 含义 |
|---|---|
| **医盾 / MedGuard** | 底层零 LLM 安全审计引擎（即论文仓库的算法层，**一行未改**） |
| **层一 / 准入** | 令牌能否发起此查询。常规权限控制，非算法创新 |
| **层二 / 审计** | 查询计划会不会泄露中间结果。**算法创新所在** |
| **SSA** | 安全敏感属性标注。逐列标注 `free` / `controlled` / `blocked` |
| **ECL** | 列的安全等级，即 SSA 的三种标签 |
| **free** | ECL 标签「自由」——可自由出现在查询中。（与 Python 内置 `free` 无关） |
| **中间结果暴露** | 子查询 SELECT 了不需要的受控列，虽不改变最终答案却泄露了信息 |
| **降级** | L0 通过 / L1 聚合替代 / L2 意图变更 / L3 已拒绝 |
| **跨域** | 两个安全域的表被个人级 JOIN，可推断出单表无法得出的信息 |
| **参考监视器** | 安全经典概念：必须拦截每次访问、不可绕过、足够小可验证 |

## 11. 安全声明（对外可引用的口径）

> 医盾引擎**零 LLM 调用、零数据库访问**，纯 AST 静态分析，单查询 < 20 ms。
>
> 这两条不是性能指标，是**安全属性**：
> 不调模型 → 没有提示注入面；不访问数据库 → 没有困惑代理面；确定性输出 → 可形式化验证。
>
> 对照实验显示：提示层防护（B4）在更换宿主模型后有效性衰减 1.4–9 倍但不归零；
> 事后过滤（B3）召回率仅 0–16.7% 且破坏功能；确定性审计（B2）跨宿主保持 100%。
>
> **已声明的边界**：本引擎不防御小样本聚合推断（如罕见病计数）。
> 该风险由准入层以全称规则覆盖，而非由审计层承担。
