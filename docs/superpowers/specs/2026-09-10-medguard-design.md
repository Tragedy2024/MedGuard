## 1. 背景与定位

### 1.1 产品

> **医患信息数据服务云平台** —— 让不会写 SQL 的医护人员和病患，用大白话查到权威准确的医院数据；同时保证查询的中间过程不泄露患者信息。

| 名称 | 指代 |
|---|---|
| **医患信息数据服务云平台** | 产品全称（对外交付名） |
| **医盾 MedGuard** | 底层安全引擎（算法层组件，本项目的技术品牌） |

两个目标**并列**，不分主从：

1. **不泄露中间信息** —— 安全
2. **非数据库专业人员随时获取权威准确的医院信息** —— 可用性

**当前版本**：医院数据仿真版。系统假设接入医院全量数据，本版本用等比缩小的仿真库呈现完整结构与流程。

### 1.2 用户与令牌

系统只认两类令牌：

| 令牌 | 持有者 | 数据范围 |
|---|---|---|
| **医护人员令牌** | 医生、护士等 | 所辖患者群体 |
| **病患令牌** | 病患本人 **或** 其指定负责人 | 该令牌绑定的患者数据 |

**关键设计**：

- 病患指定负责人需经医院认证——**认证过程不属于本项目工作内容**
- 系统**不区分**"病患本人"与"指定负责人"：两者是同一类令牌，权限完全相同
- 令牌与患者的绑定关系由医院侧建立，系统只消费这个绑定

边界：**系统只管"这个令牌能看什么"，不管"谁有资格拿到这个令牌"。**

### 1.2.1 登录身份与令牌是两件事

平台只有一个统一登录入口，账号带出**登录身份**：

| 身份 | 能进的页面 | 查询所用的令牌 |
|---|---|---|
| **医院管理员** | 数据源 / 安全策略 / 查询控制台 / 安全报告 | 医护令牌 |
| **医护人员** | 可查范围 / 查询控制台 / 安全报告 | 医护令牌 |
| **病患** | 可查范围 / 查询控制台 / 安全报告 | 病患令牌 |

**身份决定"能进哪些页面"，令牌决定"能查到什么数据"**——两者正交。
医护与病患的页面**完全相同**，差别只在令牌，这正是 §6.5 演示矩阵成立的前提。

管理员查询时以医护令牌发起：后端 `Token.type` 仍只有 `staff` / `patient`
两类，管理员的「管理」能力体现在**页面准入**，不体现在数据权限上。

> **「安全策略仅管理员可见」与「层二与角色无关」并不矛盾。** 后者说的是
> SSA 标注描述数据自身属性（§3.2），与谁在问无关；前者说的是**谁能改这份
> 标注**——那是平台管理职能，不是授权模型。把两者混为一谈，才会得出
> "策略页该对所有人开放"的错误结论。

身份不可在界面上随手切换——必须退出后重新登录。对一个以安全为卖点的
产品，"能随便切身份"本身就是可信度问题。

### 1.3 用户故事

**医护人员**：心内科医生想了解本科室糖尿病患者的血糖控制情况。以往要走信息科提需求、排队、等报表，不同人给的数还常常对不上。现在自己提问即可，答案直接来自主库。

**病患**：患者想查自己上次的检验结果、医生开的药怎么吃、影像报告怎么说。以往要在多个窗口和 APP 之间跑，报告还看不懂。

**共同的约束**：医院不能把患者数据交给第三方大模型。而大模型要参与，数据就得进它的上下文——**这正是本项目算法要解决的核心问题**。

### 1.4 权威准确

```
自然语言 ──LLM翻译──▶ SQL ──执行──▶ 医院主库
                          │
                          └──▶ 结果（唯一答案来源）
```

**LLM 只做翻译，不做回答。** 模型不生成任何答案内容——答案完全来自主库。同一问题必有唯一口径。

对齐论文仓库（`J:\race\AIC\NL2SQL`）的 NL2SQL 链路。

> **诚实标注**：翻译环节实测 EX 为 **62–77%**（论文仓库 MAC-SQL，BIRD/Spider）。这是公开可查的实验数字，文档与演示中如实呈现，不声称 100%。

## 2. 核心问题：中间结果暴露

### 2.1 威胁

LLM 参与查询，数据必须进它的上下文：

```
用户提问
   ↓
LLM 生成 SQL          ← 此时无数据
   ↓
数据库执行            ← 数据在医院内
   ↓
结果送回 LLM 总结     ← ★ 数据离开医院边界
   ↓
自然语言回答
```

**第 4 步是暴露点**：结果必须送回模型才能变成人话，而模型是第三方的（或至少会进日志、缓存）。数据在这一步出院了。

复杂问题会被 Agent 拆成多个子查询，每个子查询的结果都要进模型——**暴露面成倍放大**。而这些中间结果用户永远看不到，**也从未被审计过**。

### 2.2 传统控制为什么拦不住

| 控制手段 | 作用点 | 为什么失效 |
|---|---|---|
| 列掩码 | 最终输出 | 中间结果**不是**"输出" |
| 行级权限 RLS | 数据库查询 | 拦不住"合法查了、但要送进模型"的数据 |
| 数据库审计日志 | 事后 | 不阻断 |
| LLM 安全提示词 | 模型层 | **可被提示注入绕过；换宿主框架就衰减**（实测，见 §2.4） |

**这四行空白，就是医盾（算法层）的位置。**

### 2.3 算法创新

| 创新 | 内容 | 为什么是创新 |
|---|---|---|
| **① 新暴露面** | 形式化**信息剖面 I(D)**，把中间结果定义为可度量的安全边界 | 传统安全模型里这一层不存在 |
| **② 新检测维度** | 三维度审计：列级 / **跨域** / **派生信息流** | 后两个传统控制做不到——列掩码不理解 JOIN 语义，更不追踪 `CASE WHEN` 里的信息流 |
| **③ 新防御架构** | 零 LLM 确定性检测 + 投影级改写 + L0–L3 降级 | **不可被提示注入**；实测跨宿主 S-AR 100% |

`I(D) = Σ_i | A(q_i) ∩ restricted_columns − N(q_i) |`
即：中间结果里暴露的、下游并不需要的受限列总数。（`src/evaluation/metrics.py:164`）

### 2.4 为什么确定性是安全属性，不是性能优化

| | 提示词防御（B4） | 医盾（B2） |
|---|---|---|
| BIRD/Spider 宿主 | S-VR → 0 ✅ | S-AR 100% ✅ |
| **换 QSG 宿主** | 只降 1.4–9 倍，**不清零** ❌ | **S-AR 100%** ✅ |
| **能否被提示注入绕过** | **能** | **不能** ✅ |
| 事后过滤（B3） | S-AR 仅 0–16.7%，**且破坏查询功能** ❌ | — |

同一个安全提示词换个宿主就衰减——**安全性是数据属性，不是方法属性**（论文仓库 README 原话）。

"零 LLM 调用"带来三条安全属性：

| 性质 | 安全含义 |
|---|---|
| **无提示词** | **无法被提示注入**——LLM 护栏自身就是 LLM，可以被绕过 |
| **不访问数据库** | **无法被当作混淆代理**（confused deputy）去查库 |
| **确定性** | 审计路径无非确定性，**可形式化验证** |

这三条合起来即经典安全中的**引用监视器（Reference Monitor）**：完全中介 + 防篡改 + 可验证。

> **一句话价值主张**：在 Agent 和数据库之间，加一道**无法被说服**的执行点。

## 3. 两层安全模型

本系统的安全保证由两层构成，**层一不是算法创新，层二才是**。这个区分必须讲清楚，否则会把常规授权包装成研究成果。

### 3.1 层一：准入（令牌 → 能否发起此查询）

| | |
|---|---|
| **问题** | "这个令牌能看什么数据？" |
| **关乎** | **用户** |
| **时机** | **执行前** |
| **性质** | 常规授权，**非本项目创新** |

**病患令牌规则**（全称，非特例）：

> 查询计划**引用了患者数据表** ⟹ **必须绑定到令牌自身的 `patient_id`**，否则拒绝执行。

不判断"这个统计能不能反推个体"——那是**不可判定**的（需知道结果基数，而基数要查库才知道）。只判断"有没有碰其他患者的数据"。

**病患令牌允许的范围**：

| 允许 | 例子 |
|---|---|
| 本人的临床数据 | 我的检验结果、我的用药、我的影像报告、我的诊断 |
| 本人的费用数据 | 我的费用明细 |
| **不涉及患者表的医院信息** | 心内科有哪些医生、某医生什么职称 |
| 医护人员的执业信息 | 医生姓名（对外公示的执业信息，**不是患者数据**） |

**病患令牌禁止的范围**：

| 禁止 | 例子 |
|---|---|
| 任何其他患者的个人数据 | 别人的姓名、电话、诊断 |
| **任何涉及其他患者的统计数据** | 疾病分布、科室接诊量、罕见病计数 |

> **医生信息的边界**：医生**不是患者**，其执业信息（姓名、科室、职称）可查且合理。但医生的**个人联系方式**（`staff.phone`）属个人信息，在病患令牌下由**层二审计**处理——出现在中间结果或非必要位置时按 controlled 列规则拦截。这区分了"执业信息公开"与"个人信息保护"。

> **为什么统计数据也禁止**：罕见病个例少，小样本聚合可直接反推个体。既然"可反推性"不可判定，就采取全称禁止——**病患令牌不触碰任何涉及其他患者的数据**。

**规则验证**（2026-09-10 实测，sqlglot 解析 + 表引用检查）：

| 查询 | 引用表 | 绑定本人 | 判定 |
|---|---|---|---|
| 本人检验结果 | Laboratory, Patient | ✅ | 放行 |
| 本人基本信息 | patients | ✅ | 放行 |
| 其他患者统计 | Patient | ❌ | **执行前拒绝** |
| 疾病分布 | Patient | ❌ | **执行前拒绝** |
| 小样本分组 | Patient | ❌ | **执行前拒绝** |
| 医生信息 | staff | — | 放行（不涉及患者表） |

实现：sqlglot 解析（已是依赖）+ 表引用检查 + `patient_id = <令牌绑定值>` 校验。**零算法层改动。**

**医护人员令牌**：范围是"所辖患者群体"，属 RLS 式过滤，由医院策略决定。

### 3.2 层二：中间结果审计（查询计划 → 是否泄露）★ 算法创新所在

| | |
|---|---|
| **问题** | "这个查询计划执行时，中间结果暴露了什么？" |
| **关乎** | **数据与计划** |
| **时机** | **执行前**（零数据库访问） |
| **性质** | **本项目算法创新** |

**层二与角色无关。** SSA 标注描述数据自身的属性（身份证号是 blocked、姓名是 controlled、临床与费用分属不同域）——与谁在问无关。所以**安全策略每个数据源一份**，不按角色分。

### 3.3 两层的分工

> 病患问：「我的血糖和科室平均比怎么样？」
>
> **层二**：中间子查询要算科室平均 → 聚合形式 → 通过（聚合值确实不是个人级数据）。
> **层一**：但该查询引用了 Patient 表却未绑定本人 → **执行前拒绝**。

**层一拦住"你不该问这个"；层二拦住"你能问，但这条计划会多带数据出去"。**

### 3.4 边界声明

1. **列级 vs 值级**：SSA 是列级标注，不编码值或行。算法层保护的是"中间结果不含超出必要的受限列"。
2. **中介层次**：审计的是**查询计划**这一层。若 Agent 绕过计划直接执行 SQL，中介不完整。
3. **可反推性**：本系统不判断聚合结果能否反推个体（不可判定）。病患侧由层一全称禁止兜底。
4. **当前为仿真数据**，非真实医院数据。

## 4. 架构

### 4.1 分层

```
┌─────────────────────────────────────────────┐
│  产品层：医患信息数据服务云平台                │
│  前端 SPA (React) + FastAPI + SQLite         │
└──────────────────┬──────────────────────────┘
                   │ 只调用 2 个公开接口
                   ▼
┌─────────────────────────────────────────────┐
│  算法层：医盾 MedGuard（已有，一行不改）       │
│  run_security_auditor_pipeline(plan,db_id)   │
│  load_ssa(db_id, ssa_dir)                    │
└─────────────────────────────────────────────┘
```

> `annotate_database()`（LLM 辅助标注）**不在产品调用路径上**。演示库的 SSA 由团队手写（原因见 §7.3）。该函数保留在算法层，作为将来"接入真实企业库"时的候选标签生成工具。

### 4.2 核心原则：算法层一行不改

产品层是**纯适配器**。三个接触点（**导入路径经源码核实，实测于 2026-09-10**）：

```python
# ① 加载策略
from ssa.loader import load_ssa          # src/ssa/loader.py:132
ssa = load_ssa(db_id=datasource_id, ssa_dir=<数据源专属目录>)

# ② 取违规详情（UI 事件卡片用）—— 管线返回里没有这个
from auditor.base import SecurityAuditor      # src/auditor/base.py
auditor = SecurityAuditor(ssa)
audit_results = auditor.audit_all([{"id": sq["id"], "sql": sq["sql"]} for sq in plan])
# → [AuditResult(sub_query_index, violations=[Violation(...)])]

# ③ 取改写与降级（对比面板与徽章用）
from security_auditor import run_security_auditor_pipeline   # src/security_auditor.py:762
out = run_security_auditor_pipeline(
    decomposition_plan=plan,      # [{id, description, sql}, ...]
    db_id=datasource_id,
    ssa_dir=<数据源专属目录>,
)
```

> **为什么是三个而不是两个**：`run_security_auditor_pipeline` 只返回违规**计数**（`violations_before`/`violations_after` 为整数），不返回违规**详情**。UI 需要展示"哪一列、什么类型、为什么"，因此必须直接调用 `SecurityAuditor.audit_all()`。
>
> 两者都是零 LLM、零数据库访问的纯 AST 计算，可安全地各调一次。
>
> `run_security_auditor_pipeline` 位于 `src/security_auditor.py`，**不在** `src/auditor/base.py`（后者含 `SecurityAuditor` 类）。

**复用方式**：`pip install -e J:\race\AIC\NL2SQL`（论文仓库已含 `pyproject.toml`）。

### 4.3 数据流

```
用户提问（携带令牌）
    │
    ▼
NL→SQL 翻译 ──▶ [{id, description, sql}, ...]（查询计划）
    │            （演示模式：预置查询库直接给出）
    ▼
【层一】准入检查（作用于计划）──拒绝──▶ 返回原因（不查库、不执行）
    │ 通过
    ▼
【层二】run_security_auditor_pipeline ─→ 医盾引擎
    │
    ▼
{audited_plan, audit_report{passed,violations,rewrites_applied,
 rewrite_log,semantic_degradation}, degradation_level,
 degradation_message, audit_trace}
    │
    ▼
执行改写后计划 ─→ 主库 ─→ 自然语言回答
```

> **两层的顺序**：层一必须先有"计划"才能判定，因此它在 NL→SQL 之后、执行之前。两层都在**执行前**，都不访问数据库——这是它们的共同前提。

## 5. 算法层接口契约

> 以下结构经实机验证（2026-09-10）。

### 5.1 `run_security_auditor_pipeline` 返回值

> ⚠️ **`audit_report` 有三种形状，随执行路径变化**（2026-09-10 实测）。前端契约必须按"可选字段"处理，不能假设字段恒定存在。

```python
{
  "audited_plan": [{"id": 0, "description": "...", "sql": "..."}],  # 改写后
  "audit_report": { ... },        # ← 形状见下表，三种
  "degradation_level": "L0"|"L1"|"L2"|"L3",
  "degradation_message": "...",
  "audit_trace": [{"agent": "security_auditor", "decision": "rewrite_and_pass",
                   "rewrites": 1, "rationale": "..."}],
}
```

**`audit_report` 的三种形状**：

| 路径 | 键 | 说明 |
|---|---|---|
| **无 SSA** | `passed`, `violations`, `note` | `note="No SSA available"` |
| **干净**（零违规） | `passed`, `violations`(=`[]`), `dimensions_checked`, `rewrite_log`(=`[]`), `semantic_degradation` | 唯一含 `violations` 数组的路径 |
| **有违规并改写** | `passed`, `violations_before`(int), `violations_after`(int), `rewrites_applied`, `rewrite_log`, `semantic_degradation` | **无 `violations` 键**；`dimensions_checked` 消失 |

**两个关键坑**：

1. **`violations_before` / `violations_after` 是整数，不是数组。** 有违规时 `violations` 键**根本不存在**——产品层无法从管线返回中拿到违规详情。

2. **违规详情必须另行调用 `SecurityAuditor.audit_all()`**（见 §4.2 接触点 ③）。它返回 `AuditResult` 列表，每个含 `Violation` 对象：

```python
Violation(type="column_unnecessary_exposure",   # ViolationType 枚举
          sub_query_index=0,
          column="Patient.Diagnosis",           # 全限定列名
          severity="rewritable",                # ViolationSeverity 枚举
          detail="Patient.Diagnosis (ECL=controlled) is SELECTed but not consumed by any",
          tables=None, derived_expression=None,
          sub_query_id="0")
```

3. **`rewrite_log` 是字符串数组**，非结构化对象：
   `["Rule A: Removing Patient.Diagnosis (ECL=controlled, not needed downstream)"]`
   改写 diff 面板需产品层自行做 SQL 行级 diff 或解析这些字符串。

> **产品层调用策略**：先 `audit_all()` 取违规详情（用于事件卡片）→ 再 `run_security_auditor_pipeline()` 取改写与降级（用于对比面板与徽章）。两次调用都是零 LLM、零查库的纯 AST 计算。

### 5.2 六种违规类型（需产品化文案）

| 枚举值 | 严重度 | UI 标签 |
|---|---|---|
| `column_unnecessary_exposure` | rewritable | 不必要的列暴露 |
| `column_needs_aggregation` | rewritable | 需聚合化 |
| `blocked_column_in_select` | must_degrade | 禁止列出现在 SELECT |
| `cross_domain_personal_join` | degradable | 跨域个人级 JOIN |
| `blocked_column_in_derived` | must_degrade | 派生表达式引用禁止列 |
| `controlled_column_in_derived` | rewritable | 派生表达式暴露受控列 |

## 6. 产品模块

### 6.1 模块① 可查范围 / 数据源

同一入口，按登录身份分派两种视图。

**管理员 · 数据源**（平台配置视图）

- 数据源列表（名称、表数、列数、策略状态）
- "载入演示数据"一键创建 `regional_health`
- 库表结构树：物理表名/列名（等宽）与业务别名并排——管理员两边都要看得到，
  物理名是与接口/数据库核对的锚点

**医护 / 病患 · 可查范围**（业务视图）

- **零物理表名、零物理列名、零数据类型**
- 按业务域分组（患者、医护人员、就诊记录、临床记录、费用结算）
- 每个域列出可自由查询的字段（中文业务名），并按 ECL 等级给出计数
- 数据全部由策略接口派生，随策略变化，不会自说自话

> **为什么必须分成两视图**：本产品的用户是非数据库专业人员（§1.2）。向医生
> 展示 `clinical_records.impression TEXT` 对他们毫无意义，只会把产品变成
> 开发者工具——需求分析阶段已明确否决的形态。
>
> 业务别名来自策略 YAML 的 `table_aliases` / `column_aliases` 产品层字段，
> **零算法改动**（团队规范 §5.2）。别名完整性由测试守卫，漏一个即失败——
> 不靠前端回落到物理名悄悄兜底。

### 6.2 模块② 安全策略管理

**准入：仅医院管理员**（§1.2.1）。这是平台配置职能，不开放给临床用户与病患。

逐列审查界面：列名（物理名 + 业务别名）/ 标签（free·受控·禁止）/ 标注理由 /
审查状态，附跨域规则编辑区。

**产品差异化核心**：列掩码、RLS 都是"配一次就完事"，而**策略是会腐烂的资产**——新加一列即失效。本产品把策略做成一等公民的工作流。

> **"腐烂"在这里不是修辞，是精确的安全属性。** 源码核实（`ssa/loader.py:63`）：`SSALabels.get()` 在策略中找不到某列时返回 `ECLLevel.FREE`——即**未标注列默认放行**（fail-open）。因此"往库里加一列、忘了标注"的后果是医盾**静默放行**该列，既无告警也无痕迹。
>
> 界面上的「审查状态」正因为这一点从装饰变成了检测项：它对比库中实际列与策略标注，把未标注的列标出来。这是产品层能提供的、算法层看不见的价值。

### 6.3 模块③ 查询与拦截控制台（核心）

**入口**：自然语言提问框 + 示例问题下拉（按令牌类型分组）

**四面板**：

1. **分解方案** —— 逐个子查询列出，违规处高亮
2. **安全事件** —— 事件卡片（类型标签 + 列名 + 解释）
3. **改写对比** —— 改写前后 SQL diff + 改写日志 + 降级徽章
4. **准入判定** —— 层一结果（放行/拒绝 + 理由）

**层一拒绝时的用户可见文案**（统一措辞，不遮掩、不误导）：

> **「该查询涉及其他患者信息，无法提供。」**

**为什么明确说明而不是假装"查不到"**：含糊的失败会让用户反复换问法试探，既浪费资源也让用户困惑。明确告知边界是**可解释性**的体现——用户知道自己碰到了什么规则，而不是以为系统坏了。此文案对所有涉及其他患者数据的查询统一适用（个人数据与统计数据不作区分，避免通过错误信息差异反推数据存在性）。

### 6.4 模块④ 安全事件报告

历史记录列表 + 检测效能指标 + 一键导出 JSON。

## 7. 演示库设计（医院数据仿真版）

### 7.1 表结构（5 表）

| 表 | 说明 | 关键列 |
|---|---|---|
| `patients` | 患者主索引 | `patient_id`；id_card=**blocked**；name/phone/birth_date/address=**controlled**；gender/blood_type=free |
| `staff` | 医护人员 | `staff_id`；title/department/specialty=free；name/phone=**controlled**（患者可查医生信息） |
| `visits` | 就诊/住院 | `visit_id`, `patient_id`, `doctor_id`；department/visit_type/visit_date=free |
| `clinical_records` | **临床记录**（诊断/用药/检验/影像合一） | `record_id`, `visit_id`, `patient_id`；`record_type`=diagnosis·medication·lab·imaging；icd_code/diagnosis_name=**blocked**；findings/impression/severity=**controlled**；drug_name/dosage/frequency/route/test_name/result_value/unit/ref_range/modality/body_part=free |
| `billing` | 费用结算 | `bill_id`, `visit_id`, `patient_id`；amount=**controlled**，insurance_type/item_name=free |

**表间外键**：`visits.patient_id → patients`、`visits.doctor_id → staff`；`billing.patient_id → patients`、`billing.visit_id → visits`；`clinical_records.patient_id → patients`、`clinical_records.visit_id → visits`

**为什么是 5 张表不是 8**：原本 8 表中的 `diagnoses`/`medications`/`lab_tests`/`imaging` 四张表结构同构（都是 `visit_id + patient_id + 若干列`），合并为 `clinical_records` 一张，用 `record_type` 区分。**合并的收益是造数据与写标注的工作量减少约 40%**（这是 W1-W2 的关键路径），代价是演示时"诊断/用药/检验/影像"在界面上属于同一张表的四种记录类型。

> 需求中病患要查的三类内容——**医嘱用药**、**检验结果**、**影像结果**——全部保留在 `clinical_records` 中，未做任何削减。

> **设计决策：临床表反规范化 `patient_id`**。严格来说 `patient_id` 可经 `visit_id → visits` 推导，无需冗余。但层一准入规则依赖"查询中可直接出现 `patient_id = <令牌绑定值>`"这一判定——反规范化让规则保持简单、可测、无需解析 JOIN 路径。真实医院 OLTP 库普遍采用同样的反规范化。这是**有意的设计取舍**，非疏漏。

> **责任归属**：本演示库由**后端负责人统一审**——包含表结构、虚构数据、逐列 SSA 标注、跨域规则。SSA 标注需人工定案（annotator 不生成 `cross_domain_rules`，见 §7.3），审定后的 YAML 即为演示的权威策略文件。

**数据规模**：200–500 行虚构数据。用 `患者001`、`TEST-000001` 等一眼假的命名。

### 7.2 覆盖的查询场景

| 令牌 | 场景 | 涉及表 |
|---|---|---|
| 病患 | 我的检验结果 / 用药 / 影像 / 诊断 / 费用 | 患者表 + 临床表 |
| 病患 | 心内科有哪些医生 | `staff`（无患者表） |
| 医护 | 科室接诊量 / 疾病分布 / 费用统计 | 聚合 + 跨表 |

### 7.3 跨域规则（必须手写）

论文仓库 31 个库的跨域规则**实际生效数为 0**（经 `load_ssa()` 加载验证）。文件层面分两种情况：

| | 数量 | 状态 |
|---|---|---|
| Spider 库 | 20 | 有 `cross_domain_rules` 键，值为 `[]` |
| BIRD 库 | 11 | **无该键** |

**根因定性（经实测）**：这**既不是数据集的问题，也不是代码 bug，而是标注工作流缺口**——代码路径完备、数据支持、但没有任何工具或流程步骤去填这个字段。

三条证据：

1. **代码是好的**（实测）：向 `thrombosis_prediction.yaml` 写入一条规则后，审计器在"双侧非聚合 JOIN + 个人属性列"时正确触发 1 条 `cross_domain_personal_join`，在"仅单侧 / 已聚合 / 非个人列"三个负样本上均 0 误报。
2. **数据是支持的**：`thrombosis_prediction` 存在真实外键 `Examination.ID → Patient.ID`，两侧都持有 controlled 列——正是跨域规则要防的场景。
3. **从没人生成过它**：`src/ssa/annotator.py` 的提示词只要求 `column_labels`，全文无 `cross_domain` 字样。

人工审查记录证实了"留白"这一动作：

| 审查记录 | 跨域小节 | 内容 |
|---|---|---|
| BIRD（11 份） | **有** `## 跨域规则` | 统一为 **"（尚未定义）"** |
| Spider（20 份） | **没有该小节** | 结尾 "Generation Rules Used" 本身也是空的 |

**为什么留白是合理的**：列级标签可从列名推断，但跨域规则要求回答"这个库里哪些表分属不同安全域"——这是**业务判断，不是数据判断**。学术基准库没有业务上下文。论文仓库选择留白而非虚构，这个做法本身是对的。

**这正是产品的价值点**：真实医院部署时，有人能回答这个问题——信息安全负责人知道"临床诊疗"和"费用结算"是两个域。演示库必须手写：

```yaml
cross_domain_rules:
  - table_pair: [clinical_records, billing]
    join_key: visit_id
    forbid_personal_level: true
    allow_aggregate_level: true
    reason: 临床记录与费用结算属不同安全域，个人级关联可推断特定疾病的治疗成本
```

### 7.4 ⚠️ 演示库构造的硬性约束

经源码验证，以下三条决定演示能否触发：

1. **最后一个子查询的 controlled 列永不违规**
   `_audit_column_level` 中 `if is_final: continue` —— 最终子查询是给用户看的答案，controlled 列合法。**违规必须落在中间子查询上**。这与产品叙事（中间结果进入上下文窗口）一致。
   `blocked` 列无此豁免。

2. **纯聚合表达式会被派生审计跳过**
   `_audit_derived_info_flow` 开头 `if isinstance(expression_body, (exp.Column, exp.AggFunc)): continue`。
   `MAX(d.diagnosis_name)` 不触发；`CASE WHEN d.diagnosis_name LIKE ...` 触发。

3. **`is_personal_attribute()` 是子串匹配**
   `'name' in col_lower` —— `diagnosis_name` 会被判为个人属性。列名需避开此类误伤。

```
    │   ├── seed.py            建 5 张表 + 灌虚构数据
    │   ├── ssa/regional_health.yaml   ← 手写，含跨域规则
    │   └── queries.json       预设查询库（按令牌分组）
    ├── data/                  运行时生成（gitignore）
    │   ├── medguard.db        平台元数据
    │   └── regional_health.db 演示业务库
    └── docs/
```

**设计要点**：平台元数据库（`medguard.db`）与演示业务库（`regional_health.db`）**分离**——前者是平台自身状态，后者是被审计对象。

## 12. 关键设计决策

| 决策 | 理由 |
|---|---|
| 算法层一行不改 | 产品是纯适配器；`import` 即接口契约 |
| `datasource_id` 映射到 `db_id` | 每个数据源在专属目录放 YAML，调用时传 `ssa_dir`；零侵入 |
| **安全策略每数据源一份，不按角色分** | SSA 描述数据自身属性，与谁在问无关；按角色分是把授权与审计混为一谈 |
| **层一与层二分开实现** | 层一是常规授权（非创新），层二才是算法创新；混在一起会把授权包装成研究成果 |
| 病患令牌全称禁止涉他数据 | "可反推性"不可判定（需知结果基数，而基数要查库）；全称禁止是可判定的 |
| 演示库 SSA 手写而非 LLM 生成 | annotator 不生成 `cross_domain_rules`；blocked 标签需人工定案 |
| 演示模式与端到端模式在 API 层分开 | 视频可控；契约预留扩展 |
| 平台元数据与业务库分离 | 平台状态 vs 被审计对象，职责不同 |
| 诚实地标注演示数据 | 分两条线：科学验证线（BIRD/Spider 真实数字）与产品演示线（仿真库） |
| **登录身份与令牌正交** | 身份管"能进哪些页面"，令牌管"能查到什么数据"；医护与病患页面相同、令牌不同，演示矩阵才成立 |
| **统一登录入口，身份不可随手切** | 对一个以安全为卖点的产品，"能随便切身份"本身就是可信度问题 |
| **安全策略页仅管理员可见** | 那是平台管理职能。与"层二与角色无关"不矛盾——后者说的是标注描述数据属性，前者说的是谁能改标注 |
| **界面上只用业务别名** | 面向非数据库专业人员展示物理列名会让产品退回成开发者工具（需求分析阶段已否决的形态） |
| **别名走策略 YAML 产品层字段** | 零算法改动（团队规范 §5.2），且由测试守卫完整性，不靠前端回落到物理名兜底 |

## 13. 已知风险

| 风险 | 说明 | 应对 |
|---|---|---|
| **演示库触发失败** | 三维度在基准库上零触发（跨域/派生），演示库构造必须逐条实测 | W1 完成演示库后立即验证全部预设查询 |
| **演示库工作量大** | 5 张表的结构化数据 + 逐列标注 + 跨域规则，是 W1-W2 的关键路径 | 已由 8 表降为 5 表（同构临床表合并，工作量约 -40%）；**由后端负责人统一审定** |
| **层一规则被绕过** | 若 Agent 能构造不引用患者表的等价查询 | 层二纵深防御仍在；文档声明中介层次边界 |
| **L3 未经验证** | 全量数据仅 1 列 blocked，L3 路径未在规模上检验 | 演示库 `id_card`/`diagnosis_name` 提供真实触发场景 |
| **改写语义变化** | Rule A/B/D 不保证一般语义等价；EX 不变是实测经验结果 | 文档中如实说明，不声称"由构造保证" |
| **改写 diff 需自研** | `rewrite_log` 是字符串数组 | 产品层做 SQL 行级 diff |
| **翻译准确率** | NL→SQL 实测 EX 62–77% | 演示用预置查询库；文档如实标注 |
| **论文仓库与产品漂移** | 两个仓库共存 | 用 `pip install -e` 而非复制，`import` 即契约 |
