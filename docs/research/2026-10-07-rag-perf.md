# RAG 延迟/内存验收基准（评审 A2）

**日期**：2026-10-07（本地测量，验收数据）
**基准**：`backend/scripts/bench_rag_latency.py`
**机器**：Windows 11 Pro 10.0.26200 · 32 核 · Python 3.13（.venv）
**缓存状态**：`dense_yaml.npy`(182KB) / `dense_opencmkg.npy`(30.6MB) 均在，
BGE 本地快照在；查询语料 = OpenCMKG 开启（YAML 91 + OpenCMKG 15305 条）。

## 一、测量结果（OpenCMKG=1 全量配置）

| 场景 | P50 | P95 | 最大 | 说明 |
|---|---|---|---|---|
| 热查询（40 次） | **30.2 ms** | **36.5 ms** | 71.3 ms | BGE 矩阵检索 + BM25 + RRF 融合 |
| BM25 降级路径 | **0.9 ms** | 4.5 ms | 6.6 ms | `MEDGUARD_RAG_DENSE=0`，不加载 BGE |
| 冷启动首次检索 | **24.8 s** | — | — | BGE 模型加载 + 磁盘向量加载 + 建索引（一次性） |
| 进程 RSS 增量 | **约 968 MB** | — | — | torch + BGE 模型占大头；就绪后总 RSS ≈ 1.0 GB |
| 向量矩阵 | **30.1 MB**（float32） | — | — | 主 91 条 + 辅 15305 条，与预估一致 |

对照历史（本轮优化前，同为 OpenCMKG 全量）：热查询 ~2052 ms、冷启动
~78–111 s——热查询降约 **68 倍**，且首跑之后冷启动不再含编码耗时
（语义上"冷启动"退化为"加载已缓存向量"）。

## 二、与验收目标对照

| 目标 | 达标判断 | 数据 |
|---|---|---|
| 热查询 P50 < 50 ms（含 15k 语料） | ✅ 达标 | 30.2 ms |
| 热查询 P95 < 100 ms | ✅ 达标 | 36.5 ms |
| 热查询与纯 BM25 同量级（< 数 ms） | ✅ 达标 | 30 ms（融合检索含模型编码，量级合理） |
| 缓存命中后单次检索无编码开销 | ✅ 达标 | 热查询即缓存态（500 次查询不触发任何编码） |
| 向量缓存键绑定模型+语料哈希、失配自动重建 | ✅ 有测试钉住 | 见 `test_knowledge_rag.py`（内容变/模型变均重建） |
| 峰值内存可预期 | ✅ 有数据 | 约 1.0 GB（BGE 模型主导），向量仅 30 MB |

## 三、解释与边界

- **内存大头在 torch/BGE 模型**（约 900 MB），不是向量（30 MB）。换用
  `use_fp16` 或轻量模型可进一步压；当前数值是有据可查的预期值。
- **冷启动 24.8 s** 的构成：BGE 权重加载（约 5–9 s）+ 磁盘读入 30.6 MB
  向量 + jieba 词典 + 检索器装配；**与旧版 78–111 s 的差异 = 不再对
  15k 条语料做编码**。现场演示前预热一次即可（或跑 `--warm` 打底）。
- 测量为单机单进程观察值：复跑请记录同样的机器/缓存状态/次数/分位数
  （脚本已按此输出）；不同机器（尤其 GPU、内存带宽）数值会变。
