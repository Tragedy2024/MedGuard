# MedGuard 知识库：原始数据审核与重建建议

核验日期：2026-11-15。范围：固定版本的 OpenCMKG 三元组全量结构检查、现有三份派生文件复现、QAKG 更上游公开结构化数据及采集/处理源码。没有对35万余条关系逐条做医学真实性审定，没有改动运行知识库或生产代码。

## 结论

当前数据的风险来自两个层面：网站抓取/跨库对齐本来就有污染；项目派生脚本又有解析、关系名和信息丢失问题。不能把“脚本成功复现”“检索成功”“有来源名字”当作医学可靠。建议以原始记录重建候选证据层，修复确定的工程问题，保留人工审核闸门；不建议将未经医学复核的修复结果直接替换患者端知识库。

## 全量结构及处理审核结果

### 1. 当前 JSON 可复现，但可复现不等于内容正确

用当前 `backend/scripts/build_dataset_tables.py` 在内存中重建，不写回原文件：

| 内容 | 当前条数 | 重建条数 | 主体记录一致 |
|---|---:|---:|---|
| disease_facts.json | 7,495 | 7,495 | 是 |
| symptom_departments.json 的 symptoms | 6,227 | 6,227 | 是 |
| rag_documents.json | 15,305 | 15,305 | 是 |

排除生成日期等元信息；症状别名映射单独比较，不属于上述完全一致的主体。重建曾出现“关节痛”由“关节酸痛”变成“关节疼痛”的差异。脚本候选来自 set，并按最长公共子串及长度评分，同分时缺少稳定裁决，输出存在不确定性。别名还受当前 YAML 术语清单影响。

### 2. CSV 被按普通字符串切分，丢了2,171条合法记录

原始文件共354,755行。标准 CSV 解析后354,752条有非空的三列，另外3条是空头实体的 SameAs；没有发现本次严格 CSV 解析错误。旧脚本使用 `line.split(',')`，不能正确读取带引号且字段内部含逗号的记录。

具体损失：症状459条、检查516条、科室28条、常用药44条、推荐药199条、治疗280条、并发关系91条，以及其他关系。总计2,171条是语法上可恢复的记录；恢复语法不代表这些记录医学上已通过审核。

原始第47行：`百日咳,disease_need_check,"耳,鼻,咽拭子细菌培养"`。这是合法的三列 CSV，旧脚本按逗号切成五段后直接跳过。

### 3. 并发关系名称拼错，整类25,161条没有进入事实卡

上游实际关系为 `disease_acompany_disease`，项目 `DISEASE_RELATIONS` 写成 `disease_accompany_disease`。旧脚本从原始数据读不到该名称，因此重建事实卡中有 complications 字段的疾病数为0。

修复应显式建立上游关系到内部字段的映射，加入未知关系计数与必需关系覆盖断言；不能靠代码注释宣称已提供并发症。上游关联边本身也需核验，不能将其全部当作经过证实的并发关系。

### 4. 上游已含作者署名和残缺实体

OpenCMKG 第5行把“毓卓”作为某疾病的症状，第18行有“闫鹏辉”，另有“驻站医”等。更上游 QAKG medical.json 的第1、2条记录就存在同样内容。这说明污染并非本项目 JSON 才引入。

现有黑名单已经去除了这些已知残渣，但只对已发现的字符串有效。不能由此推断其余内容都已通过专业审核，也不宜使用“所有可疑短词一律删除”的规则。

### 5. SameAs 不能作为无条件同义词表

固定原始文件可复查示例：

- 第343931行：糖尿病 → 妊娠期糖尿病。
- 第343936行：糖尿病 → 尿崩症。
- 第344317行：慢性咽炎 → 慢性龈炎。
- 第344319行：慢性咽炎 → 急性咽炎。
- 第344322行：慢性咽炎 → 化痰息风。

这些记录至少说明其同一性/类型/亚型须重审，不能让实体识别自动相互替代。按本次完整有效 CSV 统计，SameAs 涉及17,348个节点，最大无向连通分量14,782个；传递闭包会造成大规模实体混淆。它是图结构风险，不是“14,782条全部医学错误”的统计。

### 6. 派生脚本的部分规则改变了业务语义

- 每个字段只保留前5项，依据是文件出现顺序，非临床重要性。在原始症状关系中，有5,464个疾病的清洗后症状超过5项；检查关系为2,437个。以上是原始关系主体统计，未限定最终保留的7,495个疾病，不能直接当最终事实卡的受影响数。
- `DEPT_NORMALIZE` 将部分科室映射为 None，导致相关疾病不进入最终事实卡。原始科室关系中，中医综合488、儿科综合415、小儿内科283、小儿外科99条会受到相应排除规则影响。需按产品覆盖范围和医院科室配置解释这些排除，而非称其均为无效数据。
- 精神科→心理科、肛肠科→消化内科等映射是项目自定规则，不能当作上游医学事实。应保留原名和院内映射，并分别记录审核状态。
- 症状→疾病→科室的计数是图中关系分布，不是患者就诊概率或临床分诊准确率。
- QAKG 8,808条记录中，有7,976条保留多级科室数组；重建时可保留层级，不必把结构压成一个字符串。

### 7. 推荐药物关系的含义被过度概括

QAKG [建图脚本](https://github.com/liuhuanyong/QASystemOnMedicalKG/blob/master/build_medicalgraph.py)注释把 `recommand_drug` 称为“疾病－热门药品关系”，输出关系名是“好评药品”。它来自网站药品展示抓取，不能直接改写成现行指南推荐，更不能变成个人处方建议。项目本人处方记录查询与这些公开网页药物关系必须继续分开。

## 建议的重建方式

### 第一阶段：建立不可变原始层和可追踪候选层

1. 固定当前两个源文件、commit、SHA-256和获取日期；保留原文，清洗不覆盖原件。
2. OpenCMKG 使用标准 CSV；QAKG 直接读取逐行 JSON。记录每条候选的原始文件、行号/记录ID、上游字段和关系名。
3. 采用显式 schema 和关系映射，未知关系、空实体、解析错误进入隔离队列，禁止静默跳过。
4. 保留全集，前5条仅作为界面展示预算，不再成为数据底座的截断。对关系顺序、去重和同分选择做确定性处理。

### 第二阶段：分级治理，不自动“修成正确答案”

- **明确技术残渣**：空实体、格式错误、已确认作者标签，隔离并记录原因；不凭词长或模型猜测批量删医学名词。
- **实体类型或关系可疑**：SameAs、药物与疾病混用、急慢性或子型合并，默认未审核，停用自动等价扩展。
- **医学事实待确认**：保留为候选素材，不直接展示成经过医院审核的结论。药物/治疗/并发关系应优先人工复核。
- **可公开服务的证据**：补可引用的一手医学原文、发布日期/版本、适用人群、证据片段及专业复核记录，审核通过后才进入患者端相应字段。

字段建议：`entity_id、entity_type、relation、raw_value、normalized_value、source_file、source_record、source_url、source_version、review_status、review_reason`。缺失来源 URL 就明确标缺失，不能伪造回溯网页。

### 第三阶段：从审核层派生结构化表和 RAG 语料

- 两种查询共用一份规范事实底座，避免查表与检索采用不同关系含义。
- 明确疾病问科室，取已确认疾病的科室字段；症状问科室只给候选，保留院内科室配置与适用人群。
- RAG 按字段、版本、来源和审核状态过滤；未审核药物/治疗候选不进入生成证据。
- 来源描述区分“网页聚合素材”“项目整理”“专业已复核”；不能用“医院审核知识库”覆盖所有公开数据。

### 验收

修正解析和关系映射后，先比较新旧数量、条目差异与来源覆盖，再用固定盲测验证：疾病问科室、症状问科室、子型、急慢性、同名实体、拒答、药物信息边界。医学关系按类型分层抽样、由专业人员复核；自动模型可辅助筛查，不能作为唯一审核者。只在达到预先约定的工程和医学门槛后切换，保留旧索引回滚。

建议先完成工程修复与候选层构建，再做核心常见病的人工审核子集；不应直接将35万条关系全量视为可信资料。QAKG 可作为更完整的候选记录底座，但也不能原样取代已审核知识。
