# MedGuard：生产 RAG 方法调研与适配建议

核验日期：2026-11-15。本文为设计研究，不代表已经实施或测得收益。证据分为论文、厂商工程文档和本项目代码观察；公开论文结果不等于中文医疗生产效果。本报告不声称存在适用于所有任务的“最先进 RAG”。

## 结论

医盾适合“按任务选择取数方式、按证据覆盖程度决定是否生成”。保留经身份准入和 SQL 审计的本人记录查询；疾病规范名和明确字段优先精确查表；口语问法、跨条目问题和长文档知识问答进入混合检索；歧义问题先澄清，资料缺失时明确缺失。每次回答都应能追溯证据，但不必每次都执行向量召回或调用 LLM。

## 医盾建议优先实施的五件事

1. **任务路由和澄清**：本人检查/用药记录继续 SQL；规范病名查询精确事实卡；症状导诊使用结构化候选；口语、组合、解释型问题才混合召回。实体不明、疾病子型不明确时先提一个针对性问题，不把子型自动归并为父病。
2. **字段化证据与父记录回查**：文档记录 `entity_id / field / source / version / evidence_id / parent_id`，召回后回查可核验的原始字段，按问题选择症状、检查或科室事实。不要把一整张病卡里无关药品和治疗内容无差别送入提示词。
3. **带上下文的混合检索**：继续使用 BGE/BM25/RRF，增加字段过滤、实体限制、规范别名和结果去重。同一个疾病的重复条目只占一个证据槽位。先保留 YAML 人工证据，再按评测决定 OpenCMKG 的参与范围与来源权重。
4. **覆盖判定和有限纠正**：相关不等于足以回答。比如检索到两种糖尿病的名称，不能自动认定已拥有区分方法。对比较、检查、剂量等问题分别检查所需证据字段；缺哪部分就明确说哪部分缺失。可最多做一次受控改写/拆分后再检索，仍不足则澄清或展示原始资料。
5. **按任务建立对照评测**：比较现状、加路由、加字段过滤、加上下文、开第二知识源五组，固定问题与数据版本，记录回答覆盖率、应拒答时拒答率、误拒答、错误实体/子型率、主张支持率、来源正确率及冷启动/热请求 p50/p95、生成成本。生成评审从人工金标与抽样复核开始，Ragas 仅作辅助。

## 对“是否每条数据都要经过 RAG”的判断

应区分三个动作：读到数据、检索相关证据、生成答案。结构化键值查询本来就是检索，但无须先转文本、做向量召回，再让模型复述。已知 patient_id 的本人记录、指定疾病的科室、某条用药记录应直接确定性取数；得到结果后如需解释，可另外检索公开知识，权限审计始终独立。

推荐每个回答返回实际路线与数据来源，例如 `personal_sql / structured_lookup / hybrid_retrieval / clarify / insufficient`，让开发和评测能复核。界面只显示对用户有用的“本人记录”“资料解释”“资料不足”，不强迫用户理解路由术语。

## 当前代码证据与待补充项

本项目规模为 91 条 YAML 核心资料、7495 个疾病、6227 个症状和 15305 条可选 OpenCMKG 检索文档，主线程已核验。当前检索主干是 BGE + BM25 + RRF，第二知识源默认关。完整精排框架、向量数据库迁移和更大 embedding 模型都不是先决条件。

主线程代码复核反馈：`grounding.py` 的 ID/数字/药名检查不能证明语义蕴含；`lookup_disease` 包含匹配可能把子型退成父病；检索 adapter 注释称会回查完整事实卡，但 `_retrieve_context` 实际直接使用 `Doc.text`。优先补这些证据链缺口，比盲目提升模型体量更可验证。代码行号由主线程在正式方案中补充。

当前有 86 条检索金标（26 YAML、40 口语、10 无证据、10 急症）和 14 条安全评测。它们是可复用起点，不应当作医学正确性的充分证明。先补子型、比较、近义歧义、否定和缺字段的困难样例。

## 实施边界

本文只研究和提出方案，未替换运行代码、启用 OpenCMKG、恢复精排或运行线上医疗生成。任何新方案都需在本项目离线对照集验证后才能宣称提升。
